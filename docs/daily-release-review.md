## 已核实的结论

1. 前轮只读核对主库为 V14；本轮没有再次读取运行库，不能把该版本视为实时保证。
2. 当前工作树存在大量其他未提交变更。当前源码不等于生产运行镜像，也不是仅包含每日功能的发布候选。
3. V17 只新增 daily_settings、daily_records，外键引用 users；SQL 本身不依赖 V15/V16。但当前 FamilyService 已引用 WechatFamilyDeletionService 和 WechatChatContext，不能通过删除两个迁移文件得到独立每日版本。
4. V15 新增微信会话相关结构，并为 tasks、wechat_bind 增加复合唯一约束；V16 依赖 V15 的 wechat_chat_context。即使入口开关关闭，结构变更仍需独立审查和备份恢复验证。
5. 工作 Alembic 0003 为六类关联表增加 user_id，调整分类与模板唯一约束，并移除 tasks 的默认归属。旧数据保留 default，新账号不能看到这些记录。已有真实用户行时 downgrade 会拒绝删除归属。
6. 每日聚合要求工作响应逐条带本人 user_id；工作服务必须协调升级。只升级主后端可能导致来源不可用，不能把失败保存为空计划。
7. scripts/deploy.sh 会构建当前工作树全部服务并整体更新，仅备份 postgres 主库；scripts/backup-postgres.sh 也仅覆盖主库。因此现有脚本不能直接作为本次双库发布入口。它也没有加载 OAuth 覆盖层或执行 OAuth installDist。

## 回退边界

- OAuth 故障：关闭可选公网入口和远程读取，停止新服务，保留授权 Schema。
- 每日功能故障：关闭 DAILY_ENABLED，保留已有每日记录，恢复经过兼容性验证的安全应用版本。
- 工作隔离上线后不得直接回滚到旧共享数据应用。保留归属字段，优先修复或停止工作入口；整库恢复须单独评估维护窗口后新增数据损失。
- V17 逆向只允许最新迁移且每日两表为空；OAuth 逆向仅允许授权和同意为空。不能以删除用户数据满足回滚条件。
- 不使用全局 docker volume prune，不把测试资源清理范围扩大到业务卷。
