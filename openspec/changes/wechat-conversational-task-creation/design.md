## Context

当前公众号文本链路是一次性拆解：`wechat-service` 验签后把一条消息交给 backend，backend 写入 `wechat_inbound_message`，轮询作业创建 `agent_decompose_sessions` 草稿并调用 agent-service，最后发送 H5 草稿链接。该模型把“一条微信消息、一个拆解草稿、一次网页确认”绑定在一起，不能表达家庭切换、连续追问、候选修订、会话历史和长期家庭经验。动机与行为范围见 [proposal.md](./proposal.md)，可观察要求见本 change 的三份 specs。

现有边界需要保留：

- `wechat-service` 不连接业务数据库，只负责微信协议、OAuth、客服消息和平台错误收口。
- backend 是微信绑定、家庭成员关系、任务事务和所有会话状态的唯一写入方。
- agent-service 可以读取最小家庭上下文并生成建议，但不得直接确认会话或写任务。
- 微信回调需要在平台时限内完成；客服消息没有单条响应的逐 token 流式能力。
- 任务继续使用固定五值 `TaskStatus`，所有业务读取和写入必须显式携带并校验 `family_id`。
- 旧的 `agent_decompose_sessions` 与 `wechat_inbound_message` 已有线上语义和历史数据，迁移不得把旧记录误解释成新会话。

## Goals / Non-Goals

**Goals:**

- 建立由 backend 持久化和裁决的公众号任务会话状态机，支持同一微信用户在多个家庭之间安全切换。
- 把微信传输消息、会话消息、候选快照、确认事务、发送结果和家庭经验分层保存并可追溯。
- 让耗时 AI 调用、摘要和客服消息全部在短事务之外运行，同时保证同一用户消息有序、可重试且不会重复建任务。
- 复用主任务领域的校验和权限策略，以一个原子批次提交当前候选快照。
- 给分阶段发布、关闭开关和无损回滚提供明确路径。

**Non-Goals:**

- 不把现有 `agent_decompose_sessions` 改造成通用聊天存储，也不迁移其历史草稿为新会话。
- 不引入 Redis、Kafka、向量数据库或新的独立持久化服务；本阶段继续采用 PostgreSQL 表队列。
- 不让 agent-service 解析家庭切换、删除历史或确认创建等授权指令。
- 不为家庭经验引入自动执行规则；经验只影响候选建议，不能绕过确认、权限或字段校验。
- 不在本 change 统一网页端和公众号端的实时协同编辑。
- 不新增微信解绑或账号注销接口；账号生命周期的重新认证、管理员家庭处置、绑定墓碑与审计保留规则另行规划。本次生命周期接线仅覆盖已有家庭删除入口。

## Decisions

### D1. 服务职责保持“微信适配层—确定性编排层—纯推理层”

完整数据流如下：

```text
微信回调
  │ 验签、解析、2.5 秒内调用
  ▼
wechat-service
  │ POST /api/internal/wechat/conversation/messages
  ▼
backend：幂等落消息 + 快速回执
  │
  ├─ 确定性命令（选家庭、历史、取消、确认）──► 短事务更新
  │
  └─ 普通任务文本 ──► 表队列/按绑定串行消费
                         │ 受控上下文
                         ▼
                    agent-service
                    仅返回结构化动作
                         │
                         ▼
                  backend 校验并落候选修订
                         │
                         ├─ 客服消息 outbox ──► wechat-service ──► 微信
                         └─ 精确确认 ──► 原子任务批次
```

新增内部入口：

- `POST /api/internal/wechat/conversation/messages`：接收入站信封，字段至少包含 `wechat_account_id`、`openid`、`msg_id`、完整 `content` 和 `received_at`。返回只表达是否已可靠持久化及同步被动回复类型。
- `POST /api/internal/task-conversations/turn`：backend 向 agent-service 发送受控会话上下文，返回结构化动作。
- `POST /api/internal/task-conversations/summarize`：生成滚动摘要，不参与确认裁决。
- 客服消息继续复用现有 backend → `wechat-service /api/internal/kefu/send` 通道，但由 outbox 作业调用，不在业务事务内直接发送。

backend 在调用 agent-service 前后都重新校验 schema；agent-service 不获得“确认”“切换家庭”“删除历史”或任务写入工具。所有内部调用走 Docker 内网和内部密钥，Nginx 必须显式拒绝公网 `/api/internal/**`。

**替代方案：**让 wechat-service 自己保存会话会造成绑定、家庭权限与任务事务跨两个数据源；继续使用 agent-service 现有 `/chat` 则保留了无 `session_id` 时直接写任务的危险分支。因此两者均不采用。

### D2. 新建专用会话模型，不复用一次性草稿表

采用一个新增 Flyway 迁移，建立以下逻辑表；具体版本号取实现时仓库的下一个可用编号。

| 表 | 关键字段与约束 | 用途 |
|---|---|---|
| `wechat_chat_context` | `wechat_bind_id` 唯一、`user_id`、`current_family_id`、待处理选择/删除挑战、`route_revision`、处理租约 | 保存某个微信绑定的当前家庭和串行消费游标；当前家庭只是偏好，不是授权 |
| `wechat_task_conversations` | `family_id`、`wechat_bind_id`、`user_id`、`parent_conversation_id`、`status`、`paused_from_status`、`active_slot`、`current_revision`、`slot_state`、`rolling_summary`、`summary_through_message_id`、`last_activity_at`、`expires_at`、`deleted_at`、乐观锁版本 | 每个家庭的可恢复任务会话 |
| `wechat_conversation_messages` | `wechat_account_id`、`external_msg_id`、`openid`、方向、完整正文、`wechat_bind_id`、`user_id`、可空 `family_id/conversation_id`、处理状态、重试次数、租约、时间 | 保存入站、出站和系统消息；入站以 `(wechat_account_id, external_msg_id)` 唯一 |
| `wechat_candidate_versions` | `conversation_id`、`family_id`、`revision`、候选 JSONB、可读预览、来源消息、模型/提示版本、使用的经验版本 | 不可变候选快照；`(conversation_id, revision)` 唯一 |
| `wechat_task_confirmations` | `conversation_id`、`family_id`、`candidate_version_id`、确认消息、确认用户、幂等键、提交时间 | 一次精确确认的事务凭据；候选版本和幂等键都唯一 |
| `wechat_confirmation_tasks` | `family_id`、`confirmation_id`、`task_id`、候选项序号、初始快照、最近观察指纹 | 关联最终任务并为经验学习提供可靠来源 |
| `wechat_message_outbox` | `message_id`、`dedupe_key`、序号、`not_before`、状态、次数、下次重试时间、微信错误码 | 保证渐进式客服消息有序、可重试且不重复业务动作 |
| `family_task_experiences` | `family_id`、规范化键、值/适用范围 JSONB、状态、置信度、证据数、版本、激活来源 | 家庭长期经验，与聊天摘要分离 |
| `family_task_experience_evidence` | `family_id`、经验、来源类型/标识、独立性键、内容哈希、时间 | 证明经验来源；同一任务只能贡献一个独立计数 |

所有会话、候选、确认、任务关联和经验表都直接保存 `family_id` 并建立以 `family_id` 开头的索引。能使用复合外键的地方以 `(对象 id, family_id)` 约束父子家庭一致性，不能只依赖应用层。

`wechat_task_conversations.active_slot` 在 `ACTIVE`、`AWAITING_CONFIRMATION` 和 `PAUSED` 时固定为 1，终态为 NULL，并对 `(wechat_bind_id, family_id, active_slot)` 建唯一约束，从数据库保证每个微信绑定在每个家庭最多一个可恢复会话。NULL 允许保留多个终态历史。

消息正文、外部消息标识、方向和创建时间一经插入不得修改；路由目标、处理状态和发送尝试属于可变元数据。长文本不再截断为旧表的 200 字符：原文以 TEXT 保存，送模型前最多取配置的 2000 字符，超限时保留原文并提示用户拆分输入。

旧 `wechat_inbound_message` 停止接收新会话流量，但保留历史和旧作业回滚能力；旧 `agent_decompose_sessions` 及 H5 草稿仍可按原链接读取和确认。

**替代方案：**扩展 `agent_decompose_sessions.messages` 看似少建表，但其状态、确认入口、消息来源和 H5 生命周期均是一份草稿模型，无法安全表达多家庭路由、不可变修订、消息投递和经验来源，故采用隔离的新模型。

### D3. 家庭路由和会话状态由 backend 确定性驱动

家庭候选只来自 `wechat_bind → user → active family_members → 未删除 families` 的实时查询，不复用登录响应缓存，也不签发访问令牌。当前有效家庭优先；没有当前选择时，优先使用绑定上下文的有效 default_family_id，否则按家庭 ID 升序选首个有效家庭。失效当前家庭或默认家庭须重新校验并安全回退，无可用家庭时返回加入家庭引导，不调用 AI。

default_family_id 是独立于 current_family_id 的持久化偏好，后续新增迁移，禁止修改已应用的 V15。支持“设置默认家庭 家庭名”和“默认家庭”；唯一名称必须在当前用户有效家庭中匹配，同名歧义拒绝。设置默认不切换当前家庭，普通切换不修改默认；默认偏好不能授予成员权限。

家庭名称仅在当前用户有效家庭中做标准化后的唯一匹配。编号只在最近一次列表挑战的短期快照中有效，挑战包含候选家庭 ID、`route_revision` 和五分钟过期时间。任何外部家庭 ID、过期编号或歧义名称都拒绝且不暴露家庭是否存在。

会话状态迁移：

```text
ACTIVE ──生成候选──► AWAITING_CONFIRMATION ──精确确认──► CONFIRMED
  ▲                         │
  └────修改需求/新信息──────┘

ACTIVE / AWAITING_CONFIRMATION ──切换家庭──► PAUSED
PAUSED ──切回家庭──► paused_from_status
任一可恢复态 ──取消/新建/超时──► CANCELLED / EXPIRED
终态“继续 N” ──► 新会话（parent_conversation_id 指向原会话）
```

“新建任务”会以原因 `NEW_CONVERSATION` 结束当前未确认会话并创建新会话；家庭切换只暂停，不终止。切回时恢复 `paused_from_status`。默认空闲 24 小时转 `EXPIRED`，不会恢复未确认候选；历史继续始终创建派生会话。

若用户未选家庭但有可用家庭，原始消息按上述默认规则一次性路由并继续处理，无需重发。显式家庭选择仍使用短期编号挑战；旧 WAITING_FAMILY 消息与选择挑战保留安全回放能力。路由写入受消息幂等键和 route_revision 保护。

每次选家庭、恢复、读取历史和确认任务都重新查询有效成员关系与最新角色。角色变化不改历史，但立即影响下一次确认。

### D4. 控制指令优先于 AI，确认必须携带候选修订

backend 先使用小型、可单测的确定性命令解析器，优先级固定为：

1. 默认家庭设置/查询、家庭列表、编号选择、唯一名称切换；
2. “新建任务”“当前摘要”“取消会话”；
3. “历史会话”“继续 N”“删除 N”“清空历史”及对应二次确认；
4. “确认创建 [修订号]”；
5. 其余文本才进入 AI 会话。

删除挑战和任务确认使用不同前缀，避免“确认”一词误触发。历史删除采用五分钟挑战，例如“确认删除 2”“确认清空”；未带挑战或编号变化时不执行。

每次候选回复明确显示“版本 N”。首个且从未发生过替换的版本可接受精确文本“确认创建”；一旦存在过旧版本，只接受“确认创建 N”。这样既保留首次操作简洁性，也能拒绝延迟到达的旧确认。任何额外修改文字、模糊肯定或旧编号都只返回当前版本，不创建任务。

agent-service 的单轮响应限定为：

- `ASK_CLARIFICATION`：简短追问及非权威 `slot_patch`；
- `PRESENT_CANDIDATE`：1～20 条候选任务、可读回复及 `slot_patch`；
- `REFUSE_OR_HELP`：说明不属于任务创建范围或给出可用指令。

响应不得包含确认、家庭切换、历史删除或工具调用。backend 验证动作枚举、长度、任务数量、字段类型、家庭内分类和成员档案引用；验证失败时不推进修订，只发送安全回退提示。slot 值始终记录来源消息和“用户原文/模型推断”标记；模型推断不等于确认，只有用户确认过的候选快照能进入任务事务。

**替代方案：**让 LLM 统一做意图识别可减少解析器代码，但会把授权和删除语义交给概率输出，且无法稳定处理重复确认，因此不采用。

### D5. PostgreSQL 表队列保证快速接收、同用户有序和崩溃恢复

微信回调只做验签、XML 防线、入站 API 调用和被动回复。backend 在一个短事务中插入消息并建立处理状态，成功后才能返回“已收到”。唯一键吸收微信重推。

若 backend 在 2.5 秒内不能确认持久化，`wechat-service` 在新会话开关开启时返回可重试的 5xx，让微信重投；不能继续沿用旧链路“无论如何都返回 200”的策略，否则服务故障期间会永久丢消息。重复投递由复合唯一键安全吸收，告警和限流用于控制持续故障造成的重试压力。

worker 以 `wechat_bind_id` 为串行键，通过 `wechat_chat_context` 的带过期租约一次只处理该绑定最早的可处理消息。数据库事务只覆盖抢占、状态迁移和最终落库；AI 与微信 HTTP 调用期间不持有事务。租约到期后其他实例可接管。

AI 调用前记录会话 `route_revision/current_revision`；返回落库时锁定会话并再次比较。若家庭已切换、会话已取消或修订已推进，则丢弃过期响应并按当前状态安全重放，绝不把旧家庭响应写入新家庭。

消息处理和 outbox 均使用指数退避、最大次数和可查询的失败终态。幂等边界分别是：

- 入站：`(wechat_account_id, external_msg_id)`；
- 会话动作：入站消息 ID；
- 候选：`(conversation_id, revision)`；
- 确认：`(conversation_id, candidate_revision)` 与确认幂等键；
- 出站：业务语义化 `dedupe_key`，如 `conversation:revision:candidate`。

**替代方案：**新增 Redis Stream 或消息中间件能提高吞吐，但当前规模、部署复杂度和现有表队列经验不支持引入新基础设施；租约、CAS 和短事务已足够满足公众号私聊流量。
### D6. 确认通过统一任务命令服务原子提交

新增显式参数的 `TaskCreationCommandService`（名称可按现有包风格调整），输入为 `familyId`、`actorUserId`、来源和一组创建请求。现有 HTTP 创建入口与公众号确认入口都委托该服务，避免后台 worker 伪造 `UserContext` 或走 `DirectTaskCreator` 绕过权限。

确认事务按以下顺序执行：

1. 以 `family_id + conversation_id` 加行锁，读取当前候选修订；
2. 用确认消息中的修订号校验当前不可变快照；
3. 重新读取家庭未删除状态、成员关系和最新角色；
4. 在写入前一次性校验全部任务字段、分类、执行人档案和角色权限；
5. 插入唯一确认记录；
6. 在同一数据库事务中创建全部 `PENDING` 任务，来源沿用 `AGENT`，并写 `wechat_confirmation_tasks` 表明具体来自微信会话；
7. 更新会话为 `CONFIRMED` 并提交；
8. 提交后才写通知 outbox 和创建结果客服消息。

任一校验或写入失败会回滚确认、任务和关联记录。相同确认重试先按唯一键读取已提交结果，返回同一任务 ID 集合。外部微信通知不得发生在事务提交前；否则后续任务校验失败回滚时，用户会收到不存在任务的通知。

现有 `DecomposeSessionService.confirm` 可在后续重构中委托同一批次命令服务，但本 change 不要求迁移其数据。五值 `TaskStatus` 和已有角色策略不变；若测试暴露既有 CHILD 策略缺口，必须先补齐共享策略，不能只在微信分支特判。

**替代方案：**循环调用当前 `TaskService.create` 虽然代码少，但它依赖请求线程上下文并可能逐项触发外部通知，无法证明批次失败时零副作用，故先抽取显式领域命令边界。

### D7. 结构化状态、滚动摘要和历史恢复各自有单一职责

`slot_state` 保存当前可操作字段及其来源消息，不把摘要反解析成任务字段。候选版本保存真正可确认的完整输入。滚动摘要只用于降低模型上下文长度和给用户展示，不能授权任何写操作。

摘要输入为“上一版摘要 + 尚未覆盖的新消息”，输出固定结构：已明确事实、待确认问题、用户决定、候选概览和最后覆盖消息 ID。触发条件为累计六轮、估算上下文超过阈值、家庭切换、会话暂停或终态。backend 只在摘要游标连续时提交；发现游标断裂则从仍在保留期内的原始消息重建。

每轮 agent 上下文最多包含：

- 当前家庭和最新成员角色的最小必要字段；
- 结构化 slot 状态；
- 当前候选版本；
- 滚动摘要；
- 最近约八轮会话消息；
- 当前家庭最多五条有效经验。

“历史会话”只查询当前家庭，默认返回最近五条终态或暂停会话的时间、状态和短摘要。继续历史会话复制摘要引用和必要结构化事实到一个新会话，但不复制确认键，也不把旧候选设为当前候选。

原始微信和会话消息默认保留 30 天，摘要和候选历史默认保留 180 天，均可配置。用户删除历史时先逻辑隐藏，再由清理作业删除正文、候选和摘要；已确认任务只保留最小确认哈希、任务关联与幂等审计，不保留聊天正文。清理任务按小批量执行并记录数量，不把消息正文写日志。

本次只接入现有 `FamilyService.deleteFamily`（软删除）及 `deleteEmptyFamily`（唯一管理员退出空家庭时物理删除）。清理在原家庭删除事务内执行，不改变 OWNER 校验、最后家庭保护、退出规则及已有任务删除语义；删除失败时新增清理也必须回滚。

- 软删除：清除指向目标家庭的当前/默认家庭偏好及相关选择/历史删除挑战，必要时推进 route_revision；保留微信绑定和其他家庭路由。终止该家庭可恢复会话、隐藏历史、清除摘要/槽位并移除该家庭经验及证据；正文和候选进入已有小批量保留清理。停止该家庭后续消费和未开始的出站发送，已开始的 HTTP 不承诺撤回，陈旧 AI/摘要结果不得重新落库。
- 软删除保留原有实际任务及最小确认哈希、任务关联与幂等审计；聊天清理不额外删除任务。
- 空家庭物理删除：在原事务中清除目标家庭路由引用、终止并清理会话相关状态，按外键依赖顺序完成该家庭数据删除，沿用已有任务与关联表删除规则；通过真实 PostgreSQL 验证已确认关联不会阻塞现有退出流程。
- 所有业务清理都限定目标 family_id；不能删除整个绑定上下文，不能匿名化同一绑定在其他家庭的消息，也不能移除其他家庭经验。

现有仓库尚无微信解绑或账号注销入口。用户已确认将二者留待后续独立规划；本 change 不通过直接删除绑定或用户行来代替生命周期规则，也不把该延期项记为已实现。

### D8. 家庭经验使用独立的证据投影器，不混入会话摘要或规则模板

`rule_templates` 表示可执行的拆解/日常模板，其激活和版本语义与“家庭偏好证据”不同，因此不承载本 change 的经验。家庭经验使用独立状态 `CANDIDATE/ACTIVE/DISABLED` 和单调递增版本。

经验来源分为：

- 用户在当前家庭明确表达长期偏好：直接形成带消息来源的活动经验；
- 已确认候选与实际创建任务：立即形成候选证据；
- 微信会话创建的任务后续被修改、完成、取消或延期：由定时证据投影器读取 `wechat_confirmation_tasks` 与任务当前状态，比较初始快照和最近观察指纹，幂等地产生证据。

投影器只观察有确认关联的任务，因此普通任务不会被误认为微信经验。同一任务使用 `task:{id}` 作为独立性键，无论被反复编辑多少次都只贡献一个“独立任务”计数；三个不同任务支持相同规范化偏好后，候选经验才自动激活。用户明确确认可立即激活，明确否定则生成新版本并置 `DISABLED`。

不引入向量数据库。经验先按适用范围（任务关键词、分类、执行人或时间模式）过滤，再按“用户明确确认优先、相关度、置信度、更新时间”排序，最多取五条。实际注入的经验 ID 和版本写入候选快照，便于解释和复现。家庭切换会清空进程内上下文并从目标 `family_id` 重新查询。

经验与本轮明确输入冲突时，本轮输入始终优先。经验只能生成默认建议；分类、执行人和截止时间仍需通过当前家庭校验。证据正文随消息保留期清理后可只保留哈希、来源类型、任务 ID 和计数，活动经验本身持续到用户停用或家庭删除。

**替代方案：**直接把历史摘要塞给模型实现成本低，但无法区分推断、确认和真实任务结果，也无法解释为什么形成偏好，故不采用。

### D9. 渐进式回复由有序 outbox 模拟，不承诺 token 流

被动回复承担第一段“收到，正在处理”。worker 开始 AI 处理时写一个带 `not_before` 的“正在整理”outbox；若 AI 在快速阈值内完成，最终消息会取消尚未发送的进度消息。较慢时按序发送进度、追问或候选，确认后再发送创建结果。单轮默认最多三段，阈值和最大片段数可配置。

同一会话的 outbox 使用单调序号发送，前一条未成功或明确失败前不越序。微信 token 失效沿用现有“刷新后只重试一次”；传输异常和可重试平台错误指数退避。45015、43004 等不可立即恢复的错误进入失败终态，不改变会话、确认或任务状态。

如果最终结果因客服窗口或额度未送达，下一次有效入站会优先用被动回复或新窗口中的客服消息提示最近未读结果。出站消息及每次投递尝试都可审计，但业务状态不依赖“消息已送达”。

**替代方案：**把 agent-service SSE 原样桥接到微信会产生大量客服消息、顺序和额度不可控，且微信不提供相同传输语义，因此只保留粗粒度渐进反馈。

### D10. 多租户、安全和可观测性在每一层重复设防

- 所有 conversation、candidate、confirmation、task link、experience 查询方法签名必须包含 `family_id`，并有跨家庭同错误码测试，避免对象枚举。
- 当前家庭、消息中的家庭名、AI 返回的 ID 都不是授权凭据；授权只来自实时成员关系。
- agent-service 不接收 openid、内部密钥、完整绑定信息或不必要的家庭数据；用户原文和历史以“非系统指令”边界包装，工具调用完全禁用。
- 内部端点只监听或放行基础设施网络，Nginx 对 `/api/internal/**` 显式拒绝，生产环境内部密钥禁止使用默认值。
- 日志只记录内部消息 ID、conversation ID、family ID、动作类型和耗时；openid 只显示脱敏哈希，正文、摘要和候选不得进入常规日志。
- 候选记录模型名、提示版本、输入摘要游标和经验版本，但不保存模型思维链。
- 关键指标包括：回调持久化时延、待处理/租约过期消息数、每用户队列深度、AI 动作校验失败率、会话状态迁移冲突、重复确认命中数、outbox 各错误码、摘要重建次数、跨家庭拒绝数和经验激活数。

## Risks / Trade-offs

- **[backend 故障时返回 5xx 会触发微信重投]** → 以复合唯一键吸收重复，入口严格限时，并对持续失败和队列深度告警；相比静默 200，优先保证消息不丢。
- **[同一用户连续快速发送导致旧 AI 响应覆盖新状态]** → 按绑定租约串行消费，并在 AI 返回时比较路由与会话修订。
- **[候选确认文字在微信里无法天然关联某条消息]** → 回复中展示修订号；发生过修订后强制要求“确认创建 N”。
- **[摘要或经验包含模型误判]** → 摘要永不授权，经验需要明确确认或三个独立任务证据，本轮明确输入优先。
- **[表数量和清理作业增加运维复杂度]** → 每张表保持单一职责，统一索引、保留期、批量清理和监控；不再引入额外基础设施。
- **[任务批次事务复用现有创建逻辑时可能提前发送通知]** → 抽取显式批次命令，全部预校验，外部通知统一延后到事务提交后。
- **[旧 intake 与新 conversation 同时开启会重复处理]** → 配置校验拒绝两个处理模式同时启用；切换时先停旧 worker，再开新入口和 worker。
- **[客服窗口关闭导致用户看不到结果]** → 结果保存在会话历史，发送失败不回滚；下次入站优先补发未读结果。
- **[证据投影器只观察任务最终状态，可能折叠短时间内多次编辑]** → 经验目标是稳定偏好而非完整审计，按任务独立计数；任务完整审计若未来需要应单独建设。

## Migration Plan

1. **数据库先行**：增加新表、索引和约束，不修改旧表语义；迁移在 PostgreSQL 真机验证。新外键删除策略与本次已有家庭删除流程联测；用户注销与微信解绑的业务接线另行规划。
2. **backend 暗部署**：加入会话入口、命令解析、worker、outbox、确认批次、摘要和经验投影器，所有新 worker 默认关闭。配置启动时校验旧 intake 与新 conversation 不能同时消费。
3. **agent-service 暗部署**：加入结构化 turn/summarize 内部接口及严格 schema；不改现有 `/chat` 和旧草稿链路。
4. **wechat-service 暗部署**：入站请求增加公众号标识和完整正文，新增会话开关；旧开关仍可回退。确认 Nginx 不暴露内部端点。
5. **验证后切流**：先停 `WECHAT_INTAKE_ENABLED` 旧作业，确认无 RUNNING 遗留；再对测试 openid 或单个公众号开启新会话入口和 worker，验证单家庭、多家庭、重复投递、旧确认、客服失败和跨家庭拒绝。
6. **全量启用**：观察队列、错误码和创建幂等指标后扩大范围。旧草稿和旧入站记录保持可读，不自动转成会话。
7. **后续清理**：稳定观察期结束后另立 change 移除旧 intake 代码和配置；本 change 不删除已提交历史表或接口。

回滚以开关为主：关闭新入口和 worker后，已持久化消息、会话和 outbox 保留，修复后可以继续消费；数据库迁移不向下回滚。确需恢复旧体验时，只能在确认新 worker 完全停止后单独开启旧 intake，且不得把已进入新表的消息复制回旧队列。若 agent-service 新接口异常，消息停留在可重试状态，不创建任务。
